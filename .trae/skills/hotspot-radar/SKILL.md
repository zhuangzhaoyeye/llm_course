# 热点雷达（课程自我拓展的候选发现）

## 描述

每天 10:00 定时从 arXiv（cs.AI / cs.LG / cs.CL）与 HuggingFace Daily Papers 采集近 N 天热点，产出「候选概念清单」，再由 LLM 按 6 维「成课适配度」rubric 打分，筛出「热 + 有足够内容能成课」的候选，交给用户确认。

**定位是「发现 + 人机共筛」，不是「全自动开课」。** 雷达只负责把"最近在火、且有潜力变成课程"的概念捞出来；是否真开课、内容是否正确，仍走 `course-content` 的因果链 + 逐条核验门禁。热点概念一手来源稀缺（常只有新闻稿），这正是它难过正确性门禁的原因——雷达的价值是**降低发现成本**，不是**替代质量门禁**。

## 使用场景

触发：
- 「最近 AI 圈有什么新东西」「有什么新概念值得做成一课」「扫一遍热点」
- 「雷达跑一下」「看看有什么候选」
- 周期性地想知道课程该往哪个方向拓展

不触发：写课程内容（走 `course-content`）；评审卡片（走 `card-review`）；构建打包（走 `course-build`）。

## 铁律

1. **采集与语义分开。** 脚本只做「采集 + 可规则化信号」（upvote / 多源确认 / GitHub 仓库），语义聚类与「成课适配度」打分由 LLM 步骤完成——语义没有唯一答案，用规则硬套会产生误报（依据 `30-dev-rules.md` §8.1）。
2. **候选 ≠ 课程。** 雷达输出的「强烈建议开课」只是建议；真做课时必须重新走 `course-content` 的逐条核验，热点概念的二手来源不算一手证据。
3. **一手来源优先于热度。** 30 家媒体转述同一个词 ≠ 真范式；有原始论文 / 官方 repo / 官方文档才算独立信号（见下方「业界依据」的映射）。
4. **每日定时监控，但成课必须人确认。** 每天 10:00 定时跑「采集 + 加课判断」，产出「建议加课」候选清单给用户；是否真的开课，由用户确认后走 `course-content`。雷达只到「出候选 + 建议」，不到「自动成课」。

## 每日监控工作流（定时 10:00 触发）

> 每天 10:00 由定时任务触发，跑下面 4 步，产出「建议加课」清单给用户确认。**只到「出候选 + 建议」，成课必须人确认。**

| 步 | 动作 | 谁 | 产物 |
|---|---|---|---|
| 1 | 采集 | 脚本 `radar.js --json` | 候选清单（含 upvote / 来源） |
| 2 | 判断热度 | 规则：HF upvote ≥ 15 | 热点候选 |
| 3 | 判断能否成课 | LLM 按 6 维 rubric 打分 + 联网核验一手来源 | 三档：强烈建议 / 候选 / 忽略 |
| 4 | 确认 | 用户 | 只对「强烈建议」问是否开课 |

### 加课判断标准（第 3 步，两个条件 AND）

1. **热**：HF upvote ≥ 15，或 arxiv∩hf 双源确认（排除假 spike）。
2. **有足够内容能成课**：范式级（非名词级）+ 有官方 repo / 一手来源 + 能做计算走查 + rubric ≥ 10 分。

两个都满足才进「建议加课」，否则归「候选 / 忽略」。**宁可漏，不可错**——热点错了要浪费一次逐条核验，成本远高于漏掉一个。

### 与用户确认的格式

```text
[日期] 今日监控：共 N 条候选，值得加课 M 条
- 强烈建议：<topic>（rubric 分 / 一手来源 / 为什么能成课）
- 候选：<topic>（差在哪，观察是否术语收敛）
- 忽略：<topic>（为什么）
需要你确认：是否对「强烈建议」立项成课？
```

## 指令

```bash
node .trae/skills/hotspot-radar/scripts/radar.js --days 3     # 近 3 天（默认）
node .trae/skills/hotspot-radar/scripts/radar.js --days 7     # 近 7 天
node .trae/skills/hotspot-radar/scripts/radar.js --json       # 原始 JSON（交给 LLM 打分）
```

脚本会：抓 arXiv（`export.arxiv.org/api/query`，按 submittedDate 降序）+ HuggingFace（`/api/daily_papers`）→ 按标题归一化合并去重 → 按 HF upvote 排序 → 输出候选清单（含标题 / upvote / 来源 / 摘要）。

## 三层架构

| 层 | 谁做 | 做什么 |
|---|---|---|
| **采集层** | 脚本 | arXiv + HuggingFace 抓取、合并去重、按热度排序 |
| **信号层** | 脚本 | 可规则化信号：HF upvote、多源确认（arxiv∩hf）、GitHub 仓库存在性 |
| **语义层** | LLM | 话题聚类、成课适配度 6 维打分、产出「建议开课 / 候选 / 忽略」三档 |

脚本只做前两层；拿到 `--json` 后，按下方 rubric 让 LLM 对每个候选打 6 维分。

## 业界依据（为什么这样设计）

| 来源 | 做法 | 本项目映射 |
|---|---|---|
| Paper Espresso（arXiv 2604.04562） | LLM 生成结构化摘要 + 话题标签，多时间粒度（日/周/月）聚合 | 用 LLM 做语义聚类，不做纯关键词 |
| Snapchat LLM 趋势检测（arXiv 2604.27131） | 用**独立用户数 UU**（而非浏览量）判断趋势，排除推荐算法假 spike；`lift(N,t) = numuser(t) / num_max_avg(N,t-1)` | **独立一手来源数** ＞ **媒体转载数**：一篇论文被 30 家媒体转述是假 spike，有原始论文 + 官方 repo 才算真信号 |
| Kleinberg 2002 burst detection | 经典突发检测 | 作为「热度是否仍在上升」的参考，未实现（可扩展） |

核心洞察：**热度的真假取决于信号是否独立。** 推荐算法能把一个词刷上热搜（浏览量大），但独立用户数不会同步涨。课程的对应物是：媒体转载量是「浏览量」，一手来源（论文/官方 repo/官方文档）是「独立用户数」——后者才是能做成系统化课程的证据。

## 成课适配度 rubric（6 维 × 0–2 分，满分 12）

> 由 LLM 对每个候选打分，每维给 0/1/2 分 + 一句理由。**打分是建议，不是门禁。**

| # | 维度 | 2 分 | 1 分 | 0 分 |
|---|---|---|---|---|
| 1 | **一手来源** | 有原始论文 + 官方 repo / 官方文档 | 只有公司博客 / 技术报告 | 只有新闻稿 / 二手解读 |
| 2 | **范式级 vs 名词级** | 是一个可推导的机制/方法（能讲"为什么需要它"） | 是已有范式的变体 | 只是一个新名词 / 品牌名 |
| 3 | **可计算走查** | 能从最小例子推出数字（符合 `course-content` 计算走查标准） | 有公式但难做最小走查 | 纯定性描述，无数可算 |
| 4 | **课程链衔接** | 能接续现有课程的推理链（如 Transformer → 注意力 → …） | 是现有课的一个侧面补充 | 与现有课程无关的孤岛 |
| 5 | **热度趋势** | lift>1 且多源（arxiv∩hf）确认 | 单源有 upvote | 无独立信号、只有转载 |
| 6 | **术语稳定性** | 术语已收敛、有标准学名 | 术语仍在多个叫法间漂移 | 纯营销造词、无公认定义 |

**判定**：≥10 强烈建议开课；7–9 候选（需人工判断，可先观察术语是否收敛）；≤6 不建议（大概率是假 spike 或不可课程化）。

## registry.json（跨轮去重 / 追踪）

脚本读 `registry.json` 的 `seen` 字段，给已见过的候选标 `(已见)`。写入由 LLM 步骤在打分后完成，脚本不自动改状态（避免误标）。

```json
{
  "seen": {
    "<paper-id>": {
      "title": "论文标题",
      "firstSeen": "2026-11-08T00:00:00.000Z",
      "status": "ignored | candidate | course-created",
      "score": 9,
      "note": "成课适配度分 + 一句理由"
    }
  }
}
```

## 输出格式（LLM 步骤产出的「首次实测清单」）

对 `--json` 结果聚类 + 打分后，输出一张表：

| 候选概念 | 代表论文/仓库 | upvote | 一手来源 | 适配度分 | 判定 |
|---|---|---|---|---|---|
| 认知共生体（Cognitive Symbiont） | arXiv … | 86 | 论文 | 9 | 候选 |

判定三档：`强烈建议` / `候选` / `忽略`，每档下面附一句为什么。

## 常见异常

| 现象 | 判断 |
|---|---|
| `arXiv 0 篇` | arXiv 限流（429）。脚本已内置 3 次退避重试，仍 0 篇则稍后重跑；单次请求间隔需 ≥3 秒 |
| `HuggingFace 0 条` | 网络问题或接口变更；手动 `curl https://huggingface.co/api/daily_papers` 看返回 |
| upvote 全 0 | HF 榜单上这些论文确实还没有 upvote（新上榜）；或字段结构变了（`paper.upvotes` 在嵌套对象内） |
| 合并后条目数 > 两源之和 | 不可能，说明标题归一化把不同论文误合并，查 `normTitle` 的 slice 长度 |
