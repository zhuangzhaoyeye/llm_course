# 会话交接（新开窗口无损继承）

目标：新窗口里的 agent **不问用户、不重复踩坑、不漏任务**，直接从下一步开始干。
交接物 = **一份 md（唯一事实来源）+ 一条新对话指令**。指令只负责「指向 md + 说清目标和边界」，细节全在 md 里。

## 一、何时触发

- 用户说：我要新开窗口 / 新开对话 / 开新窗口继续 / 上下文太多了 / 保存上下文 / 交接 / handoff / 帮我写个新对话的指令。
- 新对话第一句是「读 tmp/handoff_xxx.md …」→ 走 **第五节 RESUME**。
- 不触发：只是「先这样 / 结束 / 谢谢」，没有续接意图。

## 二、CREATE 流程（四步，缺一步都不算完成）

### Step 1：整理清楚这次会话的上下文（先盘点，再写）

**自动采集，不问用户：**
- `git branch --show-current`、`git status --short`、`git log --oneline -3`、`git stash list`
- 本会话改过 / 新建的文件（对照 `git status`，标出「本会话改的」和「之前就有的未提交改动」）
- 本会话产出的结果文件（`tmp/*.json` 评测结果、报告、diff 备份），以及关键数字

**从对话里提取（逐条过一遍，别凭印象）：**
1. **用户原始目标**：尽量**引用原话**（加引号），不要转述成别的意思。
2. **用户的纠正与偏好**：用户说过的「不要 / 别 / 只 / 先」——例如「不要跑全量」「先给结论」「P2 不管」「不要擅自 commit」「横屏只走官方 MCP」。这些是新窗口最容易丢的，**必须单列**。
3. **已完成**：每条附**证据**（命令、文件、数字），标 `verified`（本会话实测）/ `inferred`（推断）/ `assumed`（未验证假设）。
4. **进行中**：做到哪一步、下一步具体动作。
5. **决策与理由**：选了什么、**为什么**、否掉了什么（理由比结论重要）。
6. **试过但失败 / 被否的方案**：防止新窗口重走。
7. **未决问题 / 等用户拍板的事**。
8. **陷阱（Do not）**：已知坑、易误判点、不能碰的东西（别人的分支禁止强推、生产调用方式禁止改等）。

### Step 2：写清楚现状与正在做的任务

用三句话能说清：**在哪个分支、做到哪了、下一步干什么**。说不清就说明 Step 1 没盘点完，回去补。

> 「做到哪了」必须是**当前任务**的进度，不是本会话的动作清单。先定位当前任务的权威文档（如 `docs/产品完善方案.md`），再写进度；仓库有多条并行任务线时，本节必须点明「当前主线是哪条、其余支线别碰」。

### Step 3：写完备的 md

- 路径：`tmp/handoff_<YYYYMMDD>_<主题slug>.md`（项目约定临时产物放 `tmp/`；已存在同名就加 `_2`）。
- 体积大的原始材料（diff、长日志）**存成单独文件**放 `tmp/<主题>/` 下，md 里只写路径——引用原件，不要转述原件。
- **固定段落结构**（顺序不变，没有内容的段写「无」，不要删段）：

```markdown
# 交接：<主题> — <YYYY-MM-DD>

## 0. 一句话现状
分支 <branch>（HEAD <sha>），<做到哪>，下一步 <具体动作>。

## 1. 用户目标（原话）
> 「……」（引用用户原话；多轮目标按时间列出，最新的在最后并标「当前」）

## 2. 用户的硬性要求 / 纠正 / 偏好
- 「不要 …」— 出处/原因
- 「只 …」「先 …」

## 3. 任务清单
### 已完成（附证据，标 verified/inferred/assumed）
- [x] … — verified：<命令/文件/数字>
### 进行中
- [ ] … — 做到 <哪>，下一步 <动作>
### 待做（按优先级）
1. …
### 等用户拍板
- …

## 4. 关键决策与理由
- <决策> — 因为 <理由>；否掉了 <备选>，因为 <理由>

## 5. 方案细节 / 修法（新窗口照着做的部分）
（具体到文件、函数、行号、要改成什么；每一条可独立执行）

## 6. 试过但失败 / 已否决
- <方案> — <为什么不行>

## 7. 陷阱（Do not）
- 禁止 …

## 8. 工作区状态
- 分支 / HEAD / 未提交改动清单（本会话改的 vs 之前就有的）/ stash
- 未提交改动如何保存：<建议做法>，**需用户确认后执行**

## 9. 关键文件与产物
- `<path>` — <是什么 / 为什么重要>
- 结果文件：`<path>`（<关键数字>）

## 10. 验收标准
- <怎么判断做完了：命令 + 期望结果>

## 11. 新对话指令（复制粘贴）
<见 Step 4>
```

- 写完**以新 agent 视角读一遍**，三问自检，任一答不上就补：
  1. 我知道下一步具体干什么吗？
  2. 我知道为什么这么干、不那么干吗？
  3. 我知道什么不能碰吗？
- 自检清单（必须全过）：
  - [ ] 用户原话目标、全部纠正/偏好都在 §1 §2
  - [ ] 主题锚定了「当前任务」文档（而非只写这轮动作）；多任务线已列全并标了当前主线
  - [ ] §3 没有在任务未完成时误写「待做：无」
  - [ ] 每条「已完成」都有证据和 verified/inferred/assumed 标记
  - [ ] 引用的文件都真实存在（`ls` 核一遍）
  - [ ] 未提交改动已列全，且写明「不擅自 commit」
  - [ ] 无凭据 / token / 密码明文（只写存放位置，如「`~/.zshrc` 的 `GITLAB_TOKEN`」）

### Step 4：给一条新对话指令

- 一条，能直接粘贴；**以「读 <md 路径>」开头**，然后写：要做的事（一句话目标）+ 关键边界（不做什么）+ 验收要求 + 动手前要先确认的事。
- 指令不复述 md 细节，只引用章节号（「按 §3」「按 §5 验收」）。
- 同时把指令写进 md 的 §11，避免只存在于聊天里。
- 示例：

```text
读 tmp/handoff_20261028_mr245.md，按其中方案以本地最新代码为底，把 MR !245 的改动手工移植进来：按 §3 逐条处理适配点（时段偏好已在偏好节点、T 只抽日期，别把 time_pref/时段规则带回 T），修掉 §1 的两个 P1，P2 不管；按 §5 验收（补单测 + 3 条官方 MCP 横屏 + 已修 case 定向回归）。动手前先确认本地未提交改动怎么保存（§4），不要擅自 commit。
```

## 三、回复用户的格式

1. md 路径（项目内绝对/相对路径）+ 附带的原始材料路径。
2. 一句话说明 md 里有哪些段。
3. 新对话指令（代码块）。
4. 风险提示（只在有时写）：未提交改动、需要用户先拍板的事。

## 四、铁律

- **md 是唯一事实来源**：聊天里说过但没进 md 的信息，视为丢失。
- **锚定「当前任务」，不复述「这轮动作」**：交接主题必须是当前正在推进的那条任务线（以权威任务文档为准，如 `docs/产品完善方案.md` §九），不是「这轮顺手做了什么」。仓库同时有多条未收尾任务线时，§3 必须显式列全并标明**哪条是当前主线**、其余是「别锁到它」的支线（例：`tmp/L1_fix_progress.md` 是另一条并行线，新窗口常误锁）。
- **用户原话优先**：目标、纠正、偏好尽量引用原句；转述会走样。
- **区分实测与推断**：没测过的不写成「已验证」，没跑全量不写成「全量通过」。
- **引用原件不转述**：diff、日志、评测结果存文件，md 写路径。
- **不替用户做决定**：等拍板的事列进「等用户拍板」，新窗口先问再动。
- **不 commit / push / 改 git 状态**：交接只写文件，不动仓库状态。
- **不写凭据**。

## 五、RESUME 流程（新窗口收到「读 tmp/handoff_*.md」时）

1. **完整读 md**，再读 §9 列出的关键文件（至少读 §5 涉及的代码位置）。
2. **核对现状是否过期**：`git branch --show-current`、`git status --short`、`git log --oneline -3`，与 §8 对比；不一致就先告诉用户差异。
3. **复述确认**（一段话）：目标、边界（§2 的不要/只）、第一步动作、需要用户先确认的事（§3「等用户拍板」+ §8 未提交改动处理）。用户确认后再动手。
4. 按 §3「待做」顺序执行，按 §10 验收；过程中新的决策和发现追加回同一份 md。
5. 新窗口如果又要交接，**新建一份 md 并在开头写「接续自 <上一份路径>」**，不覆盖旧的。

## 六、参考（业界写法，已吸收）

- dennisrongo/claude-skills `handoff`：固定段落 + 每条结论标 verified/inferred/assumed + 可粘贴的 Next Session Prompt。
- softaworks `session-handoff`：CREATE / RESUME 双模式、交接前校验无 TODO 无密钥、恢复前检查是否过期。
- gsd-build `handoff`：Next action / Why / Open threads / **Do not** 四段，「下一步、为什么、不能做什么」三问自检。
- shenxingy `handoff`：Constraints & Preferences 单列用户偏好；Files 区分读过的与改过的；Meta 记分支与未提交状态。
- kingju1c3 `session-handoff`：「无损」= 用户原始目标与纠正、决策与理由、证据、失败方案、风险、下一步都要保留，缺什么要显式写出来。
